# Audit PiDog — 3 novembre 2026

Périmètre : `pidog/` (daemon, actions), `extensions/pidog-agent/` (CLI, voix,
mémoire), `extensions/pidog-monitor/`. Tout a été vérifié sur la Pi
(`mdelsinne@100.66.191.19`, Raspberry Pi 4B / 2 Go).

## 1. Ce qui était solide — non modifié

| Composant | Verdict |
|---|---|
| `pidog/service.py` (daemon) | Verrou `flock`, socket Unix, PID relu dans `/proc`, `_shutdown_dog` coupe proprement le process ultrason, retry d'init 3×, `dog_lock`. Aucune réécriture. |
| `pidog/robot_actions.py` | Catalogue fermé, palier `sit` obligatoire entre `lie` et `stand`, garde-fou tension (`6,45 V` refus / `6,90 V` ralentissement). Conservé tel quel. |
| `stream/agent_stream.py` (architecture) | 100 % asyncio, TTS phrase-par-phrase, anti-écho HFP, relance auto de `parec`. Seuls des patchs ciblés ont été appliqués. |

## 2. Défauts trouvés

### 2.1 `pidog-monitor` — boucle de redémarrage

Mesures avant correction : `NRestarts=567` en ~20 h, `WatchdogUSec=0`,
`journalctl | grep -c "Scheduled restart"` = 567.

Causes cumulées :

1. `Type=oneshot` + `Restart=on-failure` : le processus se termine (« Deactivated
   successfully ») puis systemd le relance indéfiniment.
2. `RemainAfterExit=yes` masquait l'état réel du service.
3. `WatchdogSec=120` : ignoré par systemd sur un `oneshot` (d'où `WatchdogUSec=0`).
4. `health_check` bloquait ~120 s dans `ExecStart` (`sleep 120`).
5. `ExecStartPost` mal parenthésés : `a && echo X || echo Y | logger` — le `X`
   n'arrivait jamais dans le journal.

### 2.2 Mémoire — pas du RAG

- Base SQLite sur `~/GoogleDrive/memory.db`, c'est-à-dire sur le mount **rclone
  FUSE** → `I/O error` au premier hoquet réseau, pas de `flock` fiable.
- `SELECT … LIMIT 40` : tout le contenu injecté à chaque tour, aucun retrieval,
  aucune notion de pertinence.
- Aucun cycle de vie : entrées de test, doublons (`coiffeur` vs `rdv_coiffeur`),
  dates relatives qui deviennent fausses le lendemain.
- Deux lectures de la base par tour de parole (une par module).

### 2.3 CLI — pas un agent

- Aucun `tools` : tout passait par un protocole texte `<<<CODE>>>` fragile.
- Le prompt « action » repartait d'un historique vide : pas de continuité.
- Détection `stop` par sous-chaîne : le mot « arrête » n'importe où dans une
  phrase arrêtait le daemon.
- `extract_action_code` avalait les blocs markdown du modèle.

### 2.4 Stream — trois bugs de routage

| Motif | Effet observé |
|---|---|
| `"un peu"` | baissait le volume **et** `return` → fin de tour |
| `"temps"` | déclenchait la météo (« en même temps… ») |
| `"termine"` | fermait la conversation (« je termine mon café ») |

### 2.5 Quota Groq

8 000 tokens/minute **par modèle** sur le tier gratuit. Un tour d'agent à
3 outils ≈ 7 000 tokens → 429 au 2ᵉ ou 3ᵉ tour. Deux pièges supplémentaires :

- `openai/gpt-oss-120b` est un modèle de **raisonnement** : sans
  `reasoning_effort`, le budget `max_tokens` part en « reasoning » et la réponse
  revient **vide** (`finish_reason=length`). Reproduit en direct.
- Les résultats d'outils (`journalctl`, `sys_info`) gonflaient le prompt de
  plusieurs milliers de caractères à chaque aller-retour.

## 3. Ce qui a été fait

### Prompt (`pidog_prompt.py`)

Un seul persona, deux médiums : `voice_prompt()` (TTS, 1-2 phrases, balise
d'humeur, bloc `<<<CODE>>>`) et `cli_prompt()` (markdown, chiffres, chemins,
outils). Corps du CLI en version courte (`CLI_BODY`), le détail restant
accessible via l'outil `self_info`. Prompt CLI : 4 129 car. (contre 5 300 avant
compaction).

### Mémoire (`memory.py`)

- Base **locale** `~/pidog/data/memory.db`, WAL, `busy_timeout`.
- FTS5 (`unicode61 remove_diacritics 2`) + triggers ; repli `LIKE` si absent.
- `memory_search()` : BM25 + correspondance exacte + récence + importance.
- `memory_context()` : budget 1 100 car. pour le prompt ; le reste à la demande.
- Import de l'ancienne base, fusion des quasi-doublons (Jaccard + difflib),
  désactivation du bruit.
- **Dates relatives figées** : « demain » → « demain (2026-11-04) » à
  l'écriture ; au ménage, les anciennes entrées sont datées d'après leur
  `updated_at`.
- Export JSON plat vers `~/GoogleDrive/memory-export.json` (throttlé 60 s),
  jamais de SQLite sur le mount.
- `memory_profile()` : 4 faits structurants pour le contexte de base.
- CLI : `python3 memory.py`, `memory.py search <q>`, `cleanup`, `prune`.

État actuel : 7 lignes, 5 actives (4 profil, 1 agenda), doublon fusionné.

### Outils (`tools.py`, nouveau)

14 outils : `robot_action`, `robot_state`, `robot_actions`, `memory_search`,
`memory_add`, `memory_forget`, `sys_info`, `sys_services`, `sys_logs`,
`service_ctl`, `shell`, `weather`, `media`, `self_info`.

Garde-fous **dans le code**, pas seulement dans le prompt :

- `service_ctl` refuse `start/stop/restart` sur `pidog` et
  `pidog-agent-stream` sans `explicit=true`.
- `robot_action` refuse `reboot`/`shutdown`.
- `shell` en lecture seule : liste blanche de binaires et de sous-commandes,
  refus de `; | > < \` $` et de `sudo`. `PIDOG_SHELL_MODE=full` pour tout
  autoriser.

Vérifié en direct : `service_ctl restart pidog` → refus ; `rm -rf` → refus ;
`journalctl … ; rm -rf ~` → refus ; `cat /etc/shadow` → refus noyau ; `git log`
→ OK.

### CLI (`cli/agent_cli.py`)

- Boucle agent : 6 allers-retours max, streaming SSE, exécution séquentielle des
  outils, trace `⤷ outil(...) ✓ résumé (ms)`.
- `_build_payload()` : `reasoning_effort=low` + `include_reasoning=false` pour
  gpt-oss (corrige les réponses vides).
- `MAX_TOKENS=800`, résultats d'outils plafonnés à 1 200 car.
  (`_tool_content()` tronque les plus grosses chaînes en gardant le JSON
  valide), historique 12 messages / 6 000 car.
- 429 : attente du délai annoncé, 2 reprises, puis bascule sur
  `LLM_FALLBACKS` (défaut `openai/gpt-oss-20b`), cooldown global en dernier
  recours. Message explicite si `finish_reason=length`.
- Commandes `/state /actions /mem /remember /forget /stats /model /reset /debug`.

Test réel (journal du 03/11) : « état du robot, des services et température » →
3 outils, un 429 absorbé (attente 11 s), réponse tableau + `44,8 °C`.

### Stream (`stream/agent_stream.py`)

- `robot_guardian` optionnel (une `ImportError` ne tue plus le service).
- `LLM_MODEL_VOICE` (défaut `qwen/qwen3.8-27b`) séparé de `LLM_MODEL_CLI`.
- `pgrep agent_stream.py` (l'ancien nom n'existait plus), nettoyage des
  `/tmp/pidog_tts_*.wav`, vitesse tête 30.
- Mémoire : `memory.memory_context()` au lieu du dump de 40 lignes.
- Routage : regex à frontières de mots pour stop / volume / météo ;
  `_is_closing()` pour la fin de conversation.
- 429 : une reprise si l'attente ≤ 6 s, sinon message parlé explicite (au lieu
  de « Je n'ai pas compris »).

### Monitor (`extensions/pidog-monitor/`)

`monitor.sh` réécrit + `pidog-monitor.service` (oneshot, `TimeoutStartSec=30`,
sans `Restart=` ni `WatchdogSec=`) + `pidog-monitor.timer` (`OnBootSec=2min`,
puis 15 min).

Piège corrigé au passage : `while read < <(check_*)` exécutait les contrôles
dans un sous-shell — le compteur `CRITICAL` était perdu, donc l'alerte ne
pouvait jamais se déclencher. Les contrôles tournent maintenant dans le shell
principal.

Installé et vérifié : `NRestarts=0`, timer planifié à +15 min,
`systemctl --failed` vide.
